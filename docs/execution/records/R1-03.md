## Evidence brief before implementation

- Current behavior:
  - `ProjectContextImpl.triggerGradleSync` sets `this.@activationFuture` and transitions state to `REACTIVATING`. This causes any concurrent or subsequent read calling `getCompiler()`, `getVisitor()`, or `ensureActivated()` to block on `activationFuture.join()`, waiting for the entire duration of the Gradle sync (up to 30 seconds).
  - If Gradle sync fails (e.g. offline, timeout, broken build file), `triggerGradleSync` transitions the project state to `ProjectState.FAILED`. If the project already had usable committed state (LKG snapshot, compiled classes, AST), setting state to `FAILED` blocks subsequent compilation and queries, destroying usable state.
  - If another build file change arrives while a Gradle sync is in progress, `triggerGradleSync`'s `compareAndSet` on `activationFuture` fails and the new sync is silently dropped, leaving the project with an obsolete model.
  - When a project is disposed (`dispose()` / `beginDispose()`), in-flight Gradle sync futures are not cancelled, and when the async sync completes late, its `whenComplete` callback resurrects the disposed project to `READY` or sets `FAILED`.
  - There is no labeling of stale Gradle/dependency state when sync is pending or failed while usable LKG state is retained.
  - There is no bounded retry mechanism with an explicit trigger; errors either leave the project permanently `FAILED` until manual reset or have no retry policy.
- Failure/missing behavior and smallest reproducer:
  - Simulated 30-second sync stall: calling `getCompiler()` or `ensureActivated()` blocks on `future.join()` rather than returning immediately with existing usable state.
  - Broken build sync on an already working project: project transitions to `FAILED` and usable LKG state becomes inaccessible.
  - Disposal race: disposing project while sync runs results in late completion calling `ready()` and resurrecting the disposed project.
  - Superseded sync: second sync event while first is running is ignored.
- Relevant invariant IDs and affected owner/reader/cache boundaries:
  - `INV-OWN-007` (ProjectConnection ownership: Gradle sync exclusively owns ProjectConnection, never shared concurrently).
  - `INV-OWN-008` (Cross-Project Visibility: Dependent project reads never block, always read the last committed snapshot).
  - `INV-STATE-005` (Cancellation-safe: cancellation propagates cleanly, no partial results committed).
  - `INV-STATE-008` (Reactivation Lock: REACTIVATING state exclusively owns activationFuture).
  - `INV-PERF-001` (Interactive callbacks do not synchronously compile or wait on activation/Gradle).
- Unknowns and how this task will resolve them:
  - Separate Gradle sync lifecycle from compiler activation lifecycle in `ProjectContextImpl`.
  - Add sync generation sequence and cancellation for superseded syncs.
  - Preserve usable committed LKG state on sync failure when project was previously ready.
  - Label stale sync state (`isGradleSyncInProgress`, `isGradleSyncStale`, `getLastSyncError`).
  - Implement bounded retry with backoff and explicit triggers (build file change or retry method).
  - Ensure disposal cleanly cancels in-flight sync and rejects late completion.

## Implementation decision

- Intended observable result; non-goals:
  - Existing reads during Gradle sync stalls return immediately using committed LKG state without blocking or waiting on Gradle.
  - Failed or timed-out Gradle sync preserves usable committed state if available, marking state as stale rather than destroying usable project access.
  - Superseded sync cancels the previous sync and starts the new one, discarding late results from superseded generations.
  - Disposal terminates immediately, cancels in-flight Gradle tasks, and rejects any late completion.
  - Stale state is explicitly labeled and retries are bounded with triggers.
  - Non-goals: Full dynamic classpath isolation and dependency graph invalidation across separate subprojects (owned by R2-01 and R2-02).
