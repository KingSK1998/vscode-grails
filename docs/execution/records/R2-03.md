## Evidence brief before implementation

- Current behavior: source paths and methods, with test or runtime evidence:
  1. `WorkspaceManager.groovy:288`:
     - `projectDependsOn(ProjectContextImpl source, ProjectContextImpl dependency)` uses two heuristics:
       1) `source.project.dependencies.collect { it.name }.contains(dependency.project.name)`: matches solely on raw dependency name against target project name.
       2) `jarPath.startsWith(depRootPath)`: matches if any dependency JAR's path string starts with the dependency's root directory string.
  2. Failure modes and bugs in current behavior:
     - **False positive on same-name external dependency**: If Project A depends on an external library named `"common"` (e.g. `org.apache.commons:commons-lang3`), and the workspace happens to contain an unrelated project named `"common"`, Project A falsely reports that it depends on the workspace project.
     - **False positive on sibling directory prefix**: If project A references a JAR in `/workspace/project-extra/lib.jar` and project B is located at `/workspace/project`, `jarPath.startsWith(depRootPath)` evaluates to true because `/workspace/project-extra` starts with `/workspace/project`.
     - **False negative on renamed modules**: If a module is renamed in `settings.gradle` (`rootProject.name = 'custom-name'`) or module directory path differs from dependency coordinates, name matching breaks.
     - **Composite and multi-project edges**: Gradle Tooling API models project dependencies as `IdeaModuleDependency` and evaluates explicit project dependencies, which are not currently modeled in `GrailsProject` or `WorkspaceManager`.
  3. Cycle and lock behavior:
     - `WorkspaceManager.propagateInvalidation` already implements BFS with a `visited` set to prevent infinite loops, but lacks origin/revision tracking.
- Relevant invariant IDs and affected owner/reader/cache boundaries:
  - `INV-OWN-008`: Cross-project visibility. Dependent project reads never block. Always read the last committed snapshot.
  - `INV-STATE-009`: Cross-project propagation. Edge add/remove updates downstream dirty state without waiting on upstream compilation or acquiring nested project writer locks.
  - `INV-DISC-001`: Visible framework/library facts follow resolved project/source-set membership; no leakage.
- Unknowns and how this task will resolve them:
  - How to model resolved project edges accurately across multi-project and composite builds without relying on name/string guessing: by adding explicit project edge identification (`ProjectEdge` / `ProjectDependencyEdge` or canonical module/source-set output resolution) and strict path containment matching.

## Implementation decision

- Intended observable result; non-goals:
  - Resolved build/project/source-set relationships accurately detect project-to-project dependencies across renamed modules, composite builds, and multi-project roots.
  - Unrelated projects sharing identical names or path prefixes are strictly separated (no false positives).
  - Downstream dirty notification records the triggering upstream project origin and snapshot revision.
  - Circular dependency graphs terminate with exactly one visit per node per propagation.
  - Propagation never waits on compilation and never acquires writer locks.
  - Non-goals: Full provider declaration discovery belongs to R2-04.
- Files/owners to change:
  - `GrailsProject.groovy`: Add project identity/edges (e.g. `gradleProjectPath`, `buildRoot`, `projectDependencies`).
  - `WorkspaceManager.groovy`: Update `projectDependsOn` and `propagateInvalidation` to use canonical project directory, build root + project path, and source-set output/classes containment (using path-segment matching via `isSameOrChildPath`), while recording propagation origin and revision.
  - `ProjectContextImpl.groovy`: Store invalidation origin metadata (`lastInvalidationOrigin`, `lastInvalidationRevision`).
  - `DependencyInvalidationSpec.groovy`: Add comprehensive tests covering R2-03/1, R2-03/2, and R2-03/3.
- Input revision, candidate state, commit/publication and cancellation behavior:
  - Invalidation is triggered on upstream snapshot commit, and passes the upstream snapshot version and project URI to downstream projects.
- Cache/resource impact, limits and invalidation:
  - Propagation is lightweight, non-blocking, and asynchronous.
- Alternatives considered and evidence for the smallest sufficient change:
  - Direct canonical path and output directory matching with explicit project edge support is the cleanest, robust solution that eliminates all heuristic name and string prefix guessing.
