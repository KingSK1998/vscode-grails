## Evidence brief before implementation

- Current behavior before this task: `GrailsTextDocumentService.scheduleCompilation` copied every admitted `TextFile`, stored one `PendingChange` per URI, and scheduled one runnable per URI on an unbounded `ScheduledThreadPoolExecutor` queue. Superseded work for the same URI was cancelled, and the one worker serialized compilation and close cleanup. `DocumentCompilationSpec` covered nonblocking notifications, same-URI coalescing, copied-buffer isolation, close, shutdown, blocked-worker ordering, empty input and discovery replay.
- Failure/missing behavior and smallest reproducer: distinct-URI edit storms can retain an unbounded number of copied source buffers and executor tasks; no aggregate pending-byte limit, root-fair selection, queue metrics, or root-removal cancellation exists. A deterministic blocked-compiler test spanning many URIs/roots will expose the count/byte growth and starvation.
- Relevant invariant IDs and affected owner/reader/cache boundaries: `INV-PERF-001`, `INV-PERF-002`, `INV-STATE-005`. `GrailsTextDocumentService` remains the sole owner of pending document work and its worker; `WorkspaceManager` supplies routing and root lifecycle signals; `FileContentTracker` remains the source of current editor text.

## Implementation decision

- Intended observable result; non-goals: document notifications remain prompt and apply every edit; the scheduler retains bounded metadata, alternates ready roots, recovers the latest deferred inputs, and drains lifecycle-owned tasks. R1-02 retains edit-order/open-generation correctness; R1-04 retains full coherent-publication and compiler-generation release proof.
- Files/owners changed: `GrailsTextDocumentService`, `WorkspaceManager`, `ProjectContextImpl`, `DocumentCompilationSpec`, `WorkspaceLifecycleSpec`, server status, state contract, CC-002 failure record, invariants, system map, this record, queue, and root `MEMORY.md`.
- Input revision, candidate state, commit/publication and cancellation behavior: pending tickets retain URI/version/state metadata only. The single worker copies current source immediately before compilation and records handled URI/version pairs. An overflow marker causes worker-side scanning and round-robin candidate admission; a superseded matching active ticket cannot satisfy `compilationFinished`. Close/root/shutdown invalidate queued and active candidates before publication.
- Cache/resource impact and limits: one active candidate; 256 pending tickets; 32 ordinary tickets per root; 256 KiB conservatively estimated ticket/future/map metadata using a 1 KiB base plus URI bytes; 4 MiB automatic source input. Close tickets can consume global capacity beyond the per-root ordinary limit. Global close overflow collapses to one marker and reconciles `ProjectContextImpl`'s committed overlay URI set against current buffers. All scheduler state clears on root cancellation or shutdown; overlay state clears on close/reconciliation/disposal. R1-05 owns numeric tuning.
- Alternatives considered and evidence for the smallest sufficient change: an executor task per URI cannot provide aggregate byte bounds. A separate general scheduler or lock-free queue adds ownership and lifecycle surface without evidence. One scheduled drain task plus bounded URI-keyed state fits the existing single-writer compilation model.
- Contract conflict/ADR update, if any: none expected; implementation follows the existing performance and ownership contracts.
